# 公共回合性能优化方案

更新时间：2026-03-23

## 目标

在不违反 `docs/design/gamedesign/publicturninteractiondesign.md` 的前提下，降低“点击继续回合”后的整体等待时间，并改善用户对等待过程的感知。

这份方案只讨论实现层优化，不改变以下设计语义：

- 攻击仍然走攻击交互链路
- 需要检定的行为仍然要检定
- `no_action`、洞察、观望、对抗、AOE、伤害结算等语义不变
- 设计文档要求的结构化结果仍然保留

## 当前慢的原因

公开回合“继续”按钮的执行链路不是一次模型调用，而是一个串行的多阶段流程。一次点击可能触发：

1. 段规划
2. 每个 actor 的 fallback 行为生成
3. AI 互动响应生成
4. 对抗 / 检定规则判定
5. 伤害或后果叙述补全
6. 结算摘要生成

当前实现里，多个调用都在同一请求里串行发生，前端也会等到整个 HTTP 返回后才展示结果，所以体感上会“卡很久”。

## 设计边界

优化必须满足以下边界：

- 不改公开回合交互设计的流程顺序
- 不把该检定的内容直接降级成免检
- 不把攻击、对抗、AOE、资源消耗这些规则语义合并成通用文本
- 不依赖前端伪装“已经完成”，后端结果必须真实可用

允许优化的部分：

- 减少重复 AI 调用
- 并行化彼此独立的 AI 调用
- 缓存同一回合内已经算出的中间结果
- 将非关键叙事从阻塞主链路中剥离
- 增加进度反馈与分段返回

## 主要优化方向

### 1. 先做观测，再做收敛

先把每次 continue 的关键耗时拆开，不然很难知道优化是否有效。

建议统计：

- 每次 continue 的总耗时
- 段规划耗时
- 每个 actor fallback 行为耗时
- 互动响应耗时
- 检定 / 对抗耗时
- 伤害 / 后果补写耗时
- 结算摘要耗时
- 本次 continue 内触发的模型调用次数

预期收益：

- 定位真正的热点
- 防止盲目改造导致设计语义漂移

### 2. 减少热路径上的重复 AI 调用

当前最贵的不是“有 AI”，而是“同一回合里重复问 AI”。

建议优先检查并收敛这些重复：

- 段规划里的全体 actor fallback 生成
- 互动响应里重复的目标识别 / 动作判断
- 对抗 / 伤害 / 摘要中重复的叙述生成
- 同一回合里已经算过的行动判定再次进入模型

可做的方式：

- 同一回合内复用已生成的 actor action payload
- 同一目标在同一段内只做一次动作分类
- 对“纯文案补全”设置更低优先级或改为后补

### 3. 并行化彼此独立的 actor 级请求

现在许多 per-actor 的 fallback 与响应生成是串行的。  
如果这些 actor 之间没有依赖关系，应改为并行收集，再统一合并结果。

适合并行的内容：

- 多个 NPC 的 fallback 行为生成
- 多个目标的非交互式信息整理
- 不依赖前一个 actor 输出的叙述补全

不适合并行的内容：

- 必须依赖前一步判定结果的攻击对抗
- 需要先确定命中对象后才能继续的伤害结算
- 用户输入需要即时打断的节点

注意：

- 并行化只改执行方式，不改先后语义
- 合并时必须保持设计要求的输出结构

### 4. 把“好看但不关键”的叙述移出阻塞链路

如果某些文本只是为了让结算更完整，但不影响规则结果，可以考虑延后生成。

例如：

- 结算摘要的润色文本
- 重复的场景过渡句
- 非关键的情绪补写

建议原则：

- 先返回规则结果和结构化后果
- 再异步补充叙述
- UI 上允许先显示“已结算”，再逐步补齐文案

这不会改变玩法，但会明显改善等待感。

### 5. 对“continue round”做更细的分段返回

当前的问题之一是“点击一次，直到服务器全部做完才返回”。

可考虑的实现方向：

- 在每个关键阶段返回一次进度事件
- 在前端显示“规划中 / 处理中 / 结算中 / 完成”
- 如果底层已经是 SSE 或流式通道，优先沿用已有管线

这类优化不一定减少总耗时，但会显著改善体感。

### 6. 保留设计语义前提下做确定性兜底

如果某些步骤当前主要是为了让 AI“猜一猜”，而实际上设计上允许确定性推导，就应改成规则优先，AI 仅做补充。

典型方向：

- 资源消耗按已知定义表直接扣，不再让 AI 复述判断
- 某些固定后果按模板表生成，不再二次问模型
- 已经明确 `no_action` 的情况直接走对应规则分支

前提是：

- 不能把设计要求的对抗环节删掉
- 不能把攻击流程降成普通交互

## 推荐实施顺序

### 第一阶段：低风险，先见效

1. 加耗时埋点
2. 统计每次 continue 的模型调用次数
3. 去掉明显重复的 AI 请求
4. 对不依赖彼此的 actor 级任务并行化

目标：

- 先把最慢的 20% 请求缩掉
- 不改变公开回合的规则语义

### 第二阶段：中风险，改善体感

1. 把非关键叙事改为后补
2. 做阶段性进度返回
3. 前端展示更明确的处理状态

目标：

- 总耗时可能变化不大，但“卡住感”明显下降

### 第三阶段：结构性优化

1. 重新整理 continue 的内部阶段边界
2. 让规则判定和叙事生成更彻底解耦
3. 将可缓存结果沉到 turn-level cache

目标：

- 让单次 continue 更接近“规则计算 + 少量必要 AI 调用”

## 建议优先排查的具体位置

以下位置是当前最可能的热点：

- `backend/app/services/public_turn_runtime.py`
  - continue 的外层循环与停顿点
- `backend/app/services/public_turn_segment_service.py`
  - 段规划与 per-actor fallback
- `backend/app/services/public_turn_interaction_service.py`
  - 互动响应生成
- `backend/app/services/public_turn_resolution.py`
  - 对抗、摘要、伤害补写
- `backend/app/services/world_service.py`
  - 公开回合内嵌的 action_check 判定

## 验收标准

优化完成后，至少应满足：

- 同样场景下 continue 的平均等待时间下降
- 模型调用次数可见下降，或至少不会随 actor 数量线性膨胀得太厉害
- 公开回合的攻击 / 对抗 / 检定流程仍符合设计文档
- 结构化结果仍完整保留
- 没有把原本应进入攻击链路的内容误降级成普通交互

## 不建议直接做的事

- 直接删掉对抗流程
- 用统一的静态 DC 替代攻击链路
- 把所有 AI 文案都改成模板，不做规则判定
- 为了“更快”而绕过资源消耗、命中、后果结算

这些会破坏设计文档定义的语义。

## 结论

最优先的方向不是“换更快的模型”，而是：

1. 减少 continue 内部的重复模型调用
2. 并行化无依赖的 actor 请求
3. 把非关键叙事从主阻塞链路移出去
4. 用进度反馈降低用户感知延迟

只要不改变设计语义，这四项就是当前最有价值的优化路线。
